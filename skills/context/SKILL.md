# Design Context

Given a target node, work out which flow it belongs to and load only the memory that applies. Never copy the whole memory spec into your working context: parse it in script and return only what is in scope.

1. Load `resolve`, `memory-format` and `figma-use`. Get the target node ID from the `node-id` in a Figma URL (convert `-` to `:`), or from the current selection, or ask.

2. **Find the memory.** `findMemorySpec`. When there is none but a legacy memory page exists, migrate it first (`memory-format`, Legacy memory page). When there is neither, say so and tell the designer to press Retry on the card, which runs `/design-memory:start`, instead of creating anything.

3. **Read the page structure** (`memory-format`, Page structure), first level only. With one `use_figma` script, list the top-level nodes of the target's page (`id|type|name|x,y|WxH|childCount`, never a tree, never `get_metadata` on a page), and the names of the file's other pages (a page called `Old` or `Archive` is a strong cue, recorded on the `pages:` line of `structure`). Compare with `<slug>/structure` (Read tool): unchanged ids and names mean reuse it and read nothing more. Otherwise classify only the new or renamed nodes into roles (`current`, `earlier:<name>`, `journey`, `reference`, `unclear`) and write `<slug>/structure`. The spec's `### How I read this page` bullets win over the local file: a name the designer moved or commented on keeps their role. When the roles changed, rewrite those bullets (`replaceLines`, or `addEntry` under `## What I know` the first time), in plain words. Do not mention it beyond one line when the read changed: "Read the page: V0.2.1 is current, v00 and v01 are earlier rounds."

4. **Flow chain.** Read the flow anchors from the local flow files (`<slug>/flows/*.md`, `anchor:` and `parent:`, read with the Read tool); when there are none, rebuild them from the `### Flows` bullets under `## What I know` (`memory-format`, Local cache). With `use_figma`, walk the node's ancestors (`node.parent` up to the page). A `section:<id>` anchor matches an ancestor section with that id. A `frames:<ids>` anchor matches when the target's top-level ancestor is one of the listed frames. Collect matches from innermost to outermost as the flow chain.

5. **Register a flow if the chain is empty.**
   - The anchor is the nearest section ancestor (`section:<id>`). With none (a loose top-level frame), it is the page's loose top-level frames that are not `earlier:` or `reference` (`frames:<ids>`), named after the page. Never the whole page: a page is not a flow. Say which in one line.
   - A target inside an `earlier:` section is registered like any other flow (named `<section name> (earlier round)`), because an explicit selection wins; it is simply never in scope by default.
   - Register it: allocate the next flow id (a nested id like `F-03.1` when the parent section is itself a registered flow, otherwise the next `F-0N`, taking the highest of the local flow files and the `### Flows` bullets), write `<slug>/flows/<flowId>.md` with `id`, `name`, `anchor` and `parent`, add the bullet to `### Flows` (replacing the `(no flows registered yet)` placeholder; the bullet carries the name and anchor in words, `memory-format`, What I know), and say so in one line: "Registered *<name>* as <flowId>."
   - Then ask exactly one prompt, and only for a flow you just registered: "What is *<name>* for, and for whom? (skip is fine)". This is the only question the design-memory skills ask the designer, in `start` or in a review: what a flow is for cannot be seen on the canvas. Ask it while `progress` is set in the state file (`memory-format`, Stage line; `review` sets it from its first step): a skill that wrote `progress` and then stopped is shown on the card as waiting on the terminal. Ask it once, with no follow-ups, and carry on when the designer answers or skips. Loose frames used as the anchor get the same prompt.
   - Write the `### <flowId>` brief entry under `## Brief` (`addEntry`) with `for:` (the purpose) and `who:` (the audience). A part the designer answered is written verbatim, with no marker. A part they skipped (purpose, audience, or both) becomes a best guess from the screen purposes and copy in the cached descriptions of the flow's screens (`<slug>/screens/*.md` in the shared design folder, read with the Read tool as `digest` does), written with `(inferred)` appended, when such descriptions exist. For a first-time flow none exist yet, and `review` runs `digest` right after `context`, so do not run a digest from here: write `unknown` for now, and `review` step 3 replaces it with an inferred guess once the digest has the screens. `done_when:` only if the answer covers it, otherwise `unknown`.
   - An existing flow is never asked about again, even when its mini-brief says `unknown` (keep that sentence as it is).

6. **Load entries.** Parse the spec once (`readMemoryMarkdown`, `parseMemory`) and read the entries under `## Decisions`, `## Brief` and the open questions, and the findings with `readFindings` (component instances on the design pages, plus legacy text cards on a legacy memory page). Keep an entry or finding if its scope is `file`, a flow in the chain (for ancestor flows, drop entries with `variant_only: yes`), or `frame:<nodeId>` for the target node. Drop everything else. A designer's comment on a line (`memory-format`, Entries) counts as text the designer wrote.

7. **Already considered.** Combine: the `dismissed:` lines on kept `C-` change log entries, the active decisions, and the kept findings that are still `accepted` or `deferred` (`Will do` or `On hold`). Dismissed and done findings are pruned, so they only live in the change log digest. Callers pass this list to critique skills.

8. Return: the spec's node id, the node ID, the flow chain, the page structure (roles per top-level node), the kept entries grouped by section, and the already-considered list. State the scope to the user in one line, for example: "Scope: Checkout > Guest payment (3 decisions, 2 on-hold findings)".
